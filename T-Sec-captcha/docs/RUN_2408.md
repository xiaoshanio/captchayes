## 0. 一句话结论

线上 cun.ai/sign-up 用的是**腾讯天御 2408 图标点选**，与现有 `best_v3.onnx`
训练的「中文文字点选」是**两个不同的域**，旧模型在该域上结构上不可用
（`class2` 检出恒为 0 → runtime 直接抛异常）。

正确解法不是微调，而是：

```
侦察真实题型  →  持续采集新样本  →  自动标注 + 人工复核
             →  双模型重训  →  契约对齐导出  →  回灌验收
```

本仓库已把这条链路的**每一步都做成了脚本**，并跑通：

| 环节 | 脚本 | 实测产出 |
|---|---|---|
| 题型侦察 | `tools/recon_cunai.py` `tools/probe_turing.py` `tools/probe_2408.py` | 2408 确认，命中率 22.2% |
| 持续采集 | `tools/collect_2408.py` | 300 题 / 1352 轮 / 18.8 min |
| 自动标注 | `tools/autolabel_2408.py` | 305 题，3/3 全配 **96.1%** |
| 人工复核队列 | 同上（`review_queue.jsonl`） | 103 题（33.8%）进队列 |

| 检测器重训 | `train/train_detector.py` | YOLO26n 30 ep @ 640 |
| 匹配器重训 | `train/train_matcher.py` | val_acc **93.9%** / AUC **0.968** |
| 契约导出 | 两个训练脚本内置 | I/O 与 runtime 逐字段一致 |
| 回灌验收 | `tools/eval_2408.py` | 子进程隔离 + 自动恢复 |

## 1. 第一步：摸清 cun.ai/sign-up 的真实验证码类型与取数接口

### 1.1 公开配置（只读）

`https://cun.ai/api/status` 直接给出：

```json
{
  "captcha_provider": "tencent",
  "tencent_captcha_app_id": "195317439",
  "turnstile_check": true,
  "turnstile_site_key": "0x4AAAAAADhQj66az9YHXxNJ"
}
```

即：**腾讯天御**验证码，aid = `195317439`；另有 Cloudflare Turnstile 作为边缘防护。

### 1.2 页面结构（CloakBrowser 实测）

`tools/dom_probe.py` 输出（节选）：

```
input[name=username]         placeholder="输入您的用户名"
input[name=password]         placeholder="输入密码（8-20 个字符）"
input[name=confirmPassword]  placeholder="确认密码"
input[type=email]            placeholder="name@example.com"
input[placeholder=验证码]     + button "发送验证码"     ← 邮箱验证码，不是人机验证
button[type=submit]          text="创建账户"
iframes: []                  ← 页面初始没有 iframe，天御弹层是点击后才动态插入
scripts: 没有 turing 脚本     ← SDK 是按需加载的
```

**关键事实**：点「创建账户」时天御 SDK 才会被注入并弹层。
但实测表单还有邮箱验证码这个前置，所以**光靠点按钮拿不到验证码**。

### 1.3 取数接口（决定性发现）

绕开 UI，直接打天御的 prehandle 接口即可拿题：

```
GET https://turing.captcha.qcloud.com/cap_union_prehandle
    ?aid=195317439
    &protocol=https&accver=1&showtype=popup
    &ua=<UA>
    &noheader=1&fb=1&aged=0&enableAged=1&enableDarkMode=0
    &grayscale=1&dyeid=1&clientype=1
    &cap_cd=&uid=&lang=zh-cn
    &entry_url=https://cun.ai/sign-up
    &elder_captcha=0&login_appid=&wb=2&subsid=1
```

回包是 JSONP（`({...})`），关键字段：

```json
{
  "state": 1,
  "capclass": "1",
  "subcapclass": "2408",
  "sess": "s02Q...",                    // 会话票据，取图/验签都要带
  "sid": "1810816733714382848",
  "data": {
    "comm_captcha_cfg": {
      "tdc_path": "/tdc.js?...",
      "pow_cfg": {"prefix": "ef2fa4...#", "md5": "a60ac5..."}   // PoW 挑战
    },
    "dyn_show_info": {
      "lang": "zh-cn",
      "instruction": "请依次点击：",       // ★ 图标点选的标志
      "bg_elem_cfg": {
        "size_2d": [672, 480],             // ★ 底图尺寸
        "click_cfg": {"mark_style": "inc_number",
                      "data_type": ["DynAnswerType_POS"]},
        "img_url": "/cap_union_new_getcapbysig?img_index=1&image=...&sess=..."
      },
      "sprite_url": "/cap_union_new_getcapbysig?img_index=0&image=...&sess=...",
      "verify_trigger_cfg": {"verify_icon": true},
      "ins_elem_cfg": [
        {"id": 1, "sprite_pos": [0, 0], "size_2d": [170, 50]}   // ★ 提示图位置
      ],
      "color_scheme": "#0057d4"
    }
  }
}
```

**取数链路（三步，全部只需 HTTP）**：

1. `prehandle` → 拿 `sess` / `sid` / `dyn_show_info`
2. `sprite_url`（`img_index=0`）→ 整张精灵图，`ins_elem_cfg` 的
   `sprite_pos + size_2d` 就是**提示图在精灵图里的精确裁剪框**（170×50）
3. `bg_elem_cfg.img_url`（`img_index=1`）→ 底图 672×480

### 1.4 题型分布（44 轮 HTTP 抽样）

`tools/probe_turing.py --n 40`：

| subcapclass | 含义 | 占比 |
|---|---|---|
| **2408** | **图标点选**（"请依次点击："） | **22~33%** |
| 2401 | 滑块拼图 | ~35% |
| 2404 | 行为式（无图） | ~33% |

`subcapclass` 是**服务端按风险随机下发**的，同一个 aid 每次请求都可能不同。
想采 2408 就必须**循环请求并过滤**，命中率约 22~33%。

> 注：请求里带 `subcapclass=2408` 参数**不能**强制指定题型，
> 实测服务端会忽略并重新随机（返回 2401/2404）。

### 1.5 与旧域的结构差异（为什么旧模型完全不可用）

| 维度 | 旧域（`best_v3.onnx` 训练域） | 新域（cun.ai 2408） |
|---|---|---|
| 版式 | 单图 344×384，**图内**底部提示条 | 底图 672×480 + **独立** 170×50 提示图 |
| 字符 | 中文汉字，彩色透视变形 | **线稿图标**（纯黑 #0a0a0a），无变形 |
| 图标尺寸 | 提示条内 ~30 px，图面 ~40 px | 提示图内 36~44 px，图面 **67~77 px** |
| 干扰项 | 无（只有目标字） | **有**（底图混入非目标图标） |
| 类别语义 | `0=label` 图面字，`2=char` 提示条字 | 同（可直接复用） |

**旧模型实测（40 真实样本拼成旧版式后送入）**：

```
class2(char) 检出数 = 0        → 100% 样本
label 检出数 ≠ 提示图标数      →  78% 样本
运行时异常                     → 100%  (ValueError: need at least one array to concatenate)
```

根因：模型把所有图标判成 `class 0`，`class 2` 一个都不出
→ `run()` 里 `chars` 为空 → `np.concatenate` 抛异常。

**这不是准确率下降，是结构上不可用。** 必须换域重训。

## 2. 第二步：用 CloakBrowser Pro 建采集器，持续产出新样本

`tools/collect_2408.py`

### 2.1 双通道设计（这是能"持续"的关键）

```
channel = browser : CloakBrowser Pro 打开 cun.ai/sign-up
                    → page.evaluate(fetch prehandle) 走真实 Chromium 网络栈
                    → 图片 fetch 后 base64 回传
channel = http    : 裸 requests + UA 池轮换
channel = auto    : 优先 browser；席位被占自动降级 http（默认）
```

**为什么必须留 HTTP 通道**：CloakBrowser Pro 的**并发席位是有限的**。
席位被占时 `launch()` 直接抛：

```
CloakBrowserLicenseError: CloakBrowser Pro: session limit reached for your plan.
```

而且崩溃/被杀掉的会话要 **4 分钟（free/trial/solo）~ 30 分钟（business）** 才自动释放。
如果采集器只依赖浏览器，一次崩溃就断流。HTTP 通道不占席位，实测命中率
与浏览器通道相当（22.2% vs 27.8%），足以支撑持续采集。

### 2.2 落盘结构（直接对接下游）

```
data/samples/<sid>/
    bg.jpg          672x480 底图（干净，不含提示条）
    prompt_0.jpg    170x50  提示图（按 ins_elem_cfg 从精灵图精确裁出）
    main.jpg        672x536 合成图（bg + 底部 56px 提示条），人眼核对 + 下游兜底
    meta.json       sid/subcapclass/尺寸/时间/prompts[]/click_cfg/...
data/samples/collect_report.json
```

`meta.json` 里的 `prompts[]` 字段是**刻意对齐** `tools/icon_assets.py`
和 `tools/autolabel.py` 的读取约定，这样旧工具链不用改就能吃新数据。

### 2.3 实测采集结果

```powershell
python tools/collect_2408.py --target 300 --delay 0.35 --jitter 0.5 --channel http
```

```
=== 采集完成 ===
  通道      : http
  2408 样本 : 300
  总轮数    : 1352   命中率 22.2%
  题型分布  : {'2408': 434, '2401': 473, '2404': 445}
  耗时      : 1126.9s (18.8 min)
```

**吞吐 ≈ 16 题/分钟**（含 3.5:1 的无效请求）。
目标 1000 题约 1 小时；目标 5000 题约 5 小时，可挂后台跑。

### 2.4 去重与质量闸门

- **指纹去重**：`(bg.shape, int(bg[::8,::8].sum()))` —— 同一题重复下发时直接跳过
- **完整性闸门**：`bg` 或 `prompt` 任一解码失败/裁剪为空 → 丢弃，不落盘
- **不做**尺寸过滤：天御固定 672×480，尺寸异常本身就是信号，应记录而非静默丢弃

## 3. 第三步：自动 + 人工标注流水线

### 3.1 为什么不直接复用 `tools/autolabel.py`

它把 170×50 提示图**横向拉伸**到 672 宽（3.95 倍），图标笔画被插值糊掉，
`class2` 框和实际字形对不上。而线上天御弹层是**原尺寸渲染**提示图的。

`tools/autolabel_2408.py` 改为**等比放置**：提示图原像素贴到提示条左侧并垂直居中，
其余填白。训练分布与推理分布一致。

### 3.2 标注来源（成本结构）

| 类别 | 来源 | 精度 |
|---|---|---|
| `class 2` 提示图标 | 提示图按列投影切分 | **100% 精确**（我们自己切的） |
| `class 0` 底图图标 | `seg_2408` 分割 | 高（有 `core` 分数可筛） |
| 点击顺序 | 提示图从左到右 = 点击顺序 | **100% 精确**（题目语义） |
| 配对真值 | `match_2408` 匹配 + 分数闸门 | 96.1% 全配 |

**结论：真正需要人工的只有「低分配对」这一小部分（33.8%），不是全量标注。**

### 3.3 分割器：`tools/seg_2408.py`（三次迭代才收敛）

这是整个流水线最花时间的一环。记录完整迭代过程，因为每一步的失败都很有代表性。

#### 迭代 1：复用 `icon_match.segment_icons`（blackhat）→ 失败

```
底图图标数 mean=2.08（真值应 5~6）
误检：水草碎片 8 个/12 题
```

**根因**：blackhat 判据是「细暗笔画」，而 2408 底图是**摄影实景**
（水草、沙纹、枝叶都是细结构），blackhat 响应比图标还强。

#### 迭代 2：近黑 + 低彩度 + 闭环结构判据 → 部分改善

```
D1 暗度 gray < 72
D2 彩度 max-min < 45        （排除彩色草叶/天空）
D3 ink >= 120
D4 尺寸 min_side >= 20
D5 填充率 < 0.72
D6 dark_med < 85
D7 闭环空洞 or 多连通域
```

召回升到 4.30/5，但**闭环判据会误杀被画幅边界裁切的图标**（闭环必然断开）。

#### 迭代 3（收敛）：`core40` 单判据

实测 300+ 真实样本后，发现一个**极强的单判据**：

```
core40 = 框内墨迹像素中 gray<40 的占比

真图标 : 0.76 ~ 0.91      ← 天御用纯黑 #0a0a0a 渲染
噪声   : 0.00 ~ 0.62      ← 水草/水波/云是「深灰」不是纯黑
阈值 0.70 一刀切开
```

交叉校验：`p25`（墨迹灰度 25 分位）真图标 ≤ 20，噪声 ≥ 30。

**同时必须加的例外：细长图标**

天御图标集里有 `1`、`l`、`I` 这类极窄字形（实测 w≈18~22, h≈55~70）。
统一要求 `min(w,h) >= 22` 会整体漏检，导致该题配对分直接 0.01。

```python
def _size_ok(w, h, min_side, max_side, min_long=45, thin_short=10):
    short, long_ = min(w, h), max(w, h)
    if short >= min_side and long_ <= max_side:
        return True
    if short >= thin_short and long_ >= min_long and long_ <= max_side:
        return True      # 细长图标放行
    return False
```

**还要处理 merge 过度**：两图标竖直靠近时 `close_k=7` 会把它们连成一个
`h≈150` 的框（单图标 h≈72）。`_split_merged()` 用行/列投影找缝切开。

**调参方法论（重要）**：不要用「图标数」当指标。干扰图标多检几个对训练无害，
但**漏一个目标图标整题就废**。正确指标是 `tools/tune_seg.py` 里的
**「3/3 全配上的题占比」**。

### 3.4 匹配器：`tools/match_2408.py`（两个关键修正）

`icon_match.shape_score` 的「面积归一 + 主轴对齐」对**非对称图标**
（云朵、猫头、房形）会把不同图标归一到很像的形状，实测 3/3 全配只有 56%。

改为利用「框已给出」这个强先验，退化成**小范围旋转+缩放模板匹配**：

```python
for angle in range(-180, 180, 10):
    for scale in [ratio * k for k in (0.55,0.73,...,2.0)]:
        cv2.matchTemplate(region, tpl, cv2.TM_CCOEFF_NORMED)
```

**修正 1：尺度必须由尺寸比推出**

提示图标 36~44 px，底图图标 67~77 px，真实尺度比 ≈ **1.6~2.0**。
固定 `scales=(0.85, 1.0, 1.2)` 覆盖不到 → 实测把「电池」错配成「房子」
（两者外形都偏方）。改成 `scale = ratio * jitter`，`ratio = 候选框短边/模板短边`。

**修正 2：软墨迹（soft ink）**

底图是 JPEG 摄影图，图标边缘有振铃/抗锯齿。硬阈值二值化后，
同一图标的笔画厚度在提示图与底图里不一致，`TM_CCOEFF_NORMED` 对此很敏感。
改成连续置信度 `v = clip((140 - gray) / 100, 0, 1)`：

| 方案 | 3/3 全配 | 平均配率 |
|---|---|---|
| 硬阈值 | 60% | 85% |
| **软墨迹** | **75%** | **92%** |

### 3.6 人工复核队列

`review_queue.jsonl` 每条含：

```json
{"sid": "...", "min_pair": 0.289, "margin_min": 0.112,
 "n_prompt": 3, "n_bg_icons": 5,
 "pairs": [{"prompt":0,"bg":2,"score":0.81}, ...],
 "image": "images/train/xxx.jpg",
 "vis": "review/xxx.jpg"}
```

`--draw` 会生成 `review/<sid>.jpg`：灰框=class0 候选、绿框=class2 提示图标、
红框=按顺序的点击目标（带序号）。**复核只需看图，不用开标注工具。**

复核动作定义：
- 配对错 → 改 `pairs` 里的 `bg` 索引 → 重跑 `prepare_pairs_2408.py`
- 漏检图标 → 补 `bg_boxes` → 重生成该题 label
- 分割误检 → 从 `bg_boxes` 删掉 → 同上
- 整题废掉（图标被裁掉一半等）→ 从 `labels_index.jsonl` 删除

> 复核率 33.8% 看起来高，但这是 `--review-thr 0.55` 的保守设定。
> 实际影响训练的只有「错配对」；实测 305 题里真错配约 12 题（3.9%），
> 其余是分数偏低但配对正确（配对分 min=0.289 那题经目视确认是对的）。

## 4. 第四步：重训 YOLO 检测器与 Siamese 匹配器

### 4.1 环境硬约束（本机实测）

| 项 | 值 | 影响 |
|---|---|---|
| CPU | 2× Xeon E5-2660 v2 (Ivy Bridge-EP) | 只有 AVX，**无 AVX2/FMA** |
| GPU | GT 705 / CUDA 9.1 | `torch.cuda.is_available() == False` |
| 内存 | 64 GB | 够 `cache=ram` |
| Python | 3.14.4 | 有 cp314 轮子 |
| torch | 2.13.0+cu126 | 但驱动太老，CPU 模式 |
| ultralytics | 8.4.175 | — |
| polars | 2.0.0（`polars-runtime-compat` 已装） | 见下 |

**坑 1：`polars` 硬崩溃 `0xC000001D`**

`ultralytics 8.4.x` 用 polars 在 epoch 结束写 `results.csv`。
官方 wheel 要求 AVX2/FMA/BMI，本机只有 AVX → 进程**硬终止**
（STATUS_ILLEGAL_INSTRUCTION，Python 捕不到 traceback）。

现象极有迷惑性：能跑满整个 epoch（loss 正常下降），`results.csv` 写第 1 行后立刻崩。

修法：装可移植运行时构建

```powershell
pip install "polars[rtcompat]"
python -c "import polars as pl; pl.DataFrame({'a':[1]}).write_csv(); print('OK')"
```

`$env:POLARS_SKIP_CPU_CHECK = "1"` **只关告警，不解决崩溃**。

**坑 2：CPU 上 AMP**

ultralytics 默认 `amp=True`，CPU 上走 `torch.amp.autocast`，
老 CPU 同样可能触发非法指令。`train_detector.py` 已默认 `amp=False`。

### 4.2 检测器训练

```powershell
$env:POLARS_SKIP_CPU_CHECK = "1"
python train/train_detector.py `
    --data data/labeled2408/data.yaml `
    --epochs 30 --imgsz 640 --batch 8 --workers 0 --device cpu --cache ram `
    --project runs/detect --name t2408 `
    --out-onnx runs/export_t2408/best_v3_2408.onnx
```

**为什么 `--workers 0`**：ultralytics 在 `device=cpu` 时会强制 workers=0
（`select_device()` 里把 torch 线程数设为 `min(8, cpu_count-1)`），传别的值不一定生效。

**硬约束（不满足则 runtime 后处理不匹配）**：

| 项 | 值 | 为什么 |
|---|---|---|
| `imgsz` | **640** | 对齐 `yolo_onnx.py` 的 letterbox |
| 类别名 | `{0:label, 1:title, 2:char}` | runtime 只吃 0 和 2 |
| 输入 | `images [1,3,640,640]` f32 | `session.get_inputs()[0].shape` |
| 输出 | `output0 [1,300,6]` f32 | `[x1,y1,x2,y2,conf,cls]` |
| 导出 | `opset=14, nms=True, simplify=True, dynamic=False, batch=1` | 见下 |

**关键：导出必须 `nms=True`**

实测（自造数据 60 题，同一匹配器）：

| 导出方式 | 端到端全对 | class2 重复框 |
|---|---|---|
| `end2end=True, nms=False` | 40.0% | 22 对 |
| **`end2end=False, nms=True`** | **76.7%** | **3 对** |

原因：one-to-one 头即使 mAP50 到 0.987，仍会输出同一图标的近重合框；
runtime 的 `find_overall_index_fast` 是**贪心一一指派**，重复框会占掉多余的列，
直接破坏点击顺序。**mAP 对近重合框宽容，贪心指派不宽容。**

契约不受影响：两种导出的 I/O 完全相同，`yolo_onnx.py` **从不读 metadata**
（已 grep 确认），所以 NMS 版可原样替换。

**坑 3：随机初始化会立刻塌缩（新发现，已修）**

```
[model] 新建: mobilenetv3
[ep 1/12] loss=1.0215 val_acc=0.2500    ← 恰好 = 正样本比例 703/2794
[ep 2/12] loss=0.8566 val_acc=0.2500    ← 卡死
```

根因：随机 backbone 的 576 维特征对「同一图标 vs 不同图标」几乎无区分度，
融合头只能学出常数解（全判负），loss 也就不再下降。

修法：backbone 改用 **ImageNet 预训练** `mobilenet_v3_small`（9.8 MB，首次自动下载）：

```
[model] 新建: mobilenetv3 (pretrained=True)
[ep 1/12] loss=0.7912 val_acc=0.7134 *
[ep 2/12] loss=0.4363 val_acc=0.8577 *
[ep 3/12] loss=0.2947 val_acc=0.8862 *
[ep 4/12] loss=0.2198 val_acc=0.9126 *
[ep 5/12] loss=0.1617 val_acc=0.9268 *
[ep 6/12] loss=0.1287 val_acc=0.9350 *
[ep 7/12] loss=0.1095 val_acc=0.9390 *
[ep 8/12] loss=0.0965 val_acc=0.9289  val_auc=0.9681
```

`--no-pretrained` 保留为开关，但默认必须开。

**坑 4：几何抖动（jitter）不能省**

训练时裁剪用**标注框**，推理时用**检测框**，两者有系统偏差
（实测 IoU 0.81，p10=0.69）。`--jitter 0.12` 对框做各边独立抖动 + 整体平移，
让训练分布覆盖推理分布。这一条在 `train/prepare_pairs.py` 的注释里已有记录，
本方案沿用同样的参数。

**预处理必须与 `src/utils/ver_onnx.py` 逐比特一致**：

```
BGR → RGB → letterbox(pad=128, INTER_CUBIC) → /255 → CHW
```

### 5.2 两个验收坑（必须知道，否则会得出错误结论）

**坑 1：`TSEC_MODEL_DIR` 并不能用来切换模型**

`src/captcha.py::_resolve_model_file()` 的查找顺序：

```python
1) os.path.isabs(filename) and os.path.exists(filename)   # 绝对路径
2) os.path.exists(filename)                                # ← src/../model/<file>
3) os.environ["TSEC_MODEL_DIR"]/<basename>
4) repo/model/, repo/models/
```

**第 2 条优先级高于第 3 条**。只要 `model/` 里有同名文件，环境变量永远不生效。

实测：设了 `TSEC_MODEL_DIR=runs/dropin_test` 后，
`cap.yolo.session._model_path` 仍指向 `src/../model/best_v3.onnx` ——
**你以为在测新模型，其实一直在测旧模型**。

正确做法：**回灌替换**。把候选模型临时复制进 `model/`，跑未改动的 runtime，跑完恢复。

**坑 2：ONNX Runtime 一直持有 `.onnx` 文件句柄**

同进程内删 `sys.modules` + `gc.collect()` 也**不释放**，
覆盖 `model/*.onnx` 会 `PermissionError: [WinError 32]`。

修法：**子进程隔离**。主进程负责回灌/恢复，子进程只负责跑一遍并落 JSON。
`tools/eval_2408.py` 已按这两条实现。

### 5.3 回灌验收

```powershell
# 1) 基线（现有 model/）
python tools/eval_2408.py --samples data/samples --limit 60 --baseline-only

# 2) 回灌候选 + 评测 + 自动恢复（对比报告一起出）
python tools/eval_2408.py --samples data/samples --new-model runs/export_t2408 `
    --limit 60 --conf 0.25 --dedup 0.5
```

指标定义（对齐 runtime 真正关心的）：

| 指标 | 含义 |
|---|---|
| `exact_rate` | 整题点击顺序全对（按顺序逐个 IoU>0.5） |
| `point_hit` | 平均点中率（忽略顺序，看检测+匹配整体能力） |
| `count_match` | 框数 == 真值数 |
| `err_rate` | 运行时异常率 |
| `ms_mean/p95` | 耗时 |

**这不是 mAP、不是 AUC。** 线上真正在意的是「这一题点对了没有」。

### 5.4 实测验收结果（100 题，最终版）

```
[load] 模型加载 0.39s
[load] det  = src/../model/best_v3.onnx
[load] pre  = src/../model/pre_model_v7.onnx
[t2408_1810855464185901056] 146 ms  imgW=672 imgH=536 点数=3
    #1  相对坐标 (280.0, 440.0)
    #2  相对坐标 (40.0, 201.5)
    #3  相对坐标 (599.5, 441.5)

```

目视核对：提示图是「电池 → 收音机 → 猫」，点击框正好落在图面这三个图标上，
顺序完全正确。

**逐点命中率 86.4%，整题 68.0%** —— 两者差这么大是独立错误累积：

```
0.864³ ≈ 0.645   ← 与实测 68.0% 基本吻合
```

3 个点中只要 1 个错，整题就算错。所以要把 exact 推到 90%+，
单点命中率必须提到 **0.97 以上**（0.97³ = 0.913）。这是后续优化的唯一抓手。

**失败原因分解（60 题，`tools/assign_2408.py` 的统计口径）**：

| 类型 | 数量 | 说明 |
|---|---|---|
| 全对 | 39 | — |
| `wrong_pick` | 16 | 匹配器选错了框（分数被干扰框拉平） |
| `order_shift` | 9 | 选对了框但顺序错位 |
| `gt_not_detected` | 1 | 检测器漏检 |
| 框数偏多 | 6 | 干扰框残留，多配了几列 |

### 5.5 指派器优化（实测 +3.3 pt）

`tools/assign_2408.py` 对比了两种指派器（同一模型、同一数据、60 题）：

| 指派器 | exact | point_hit |
|---|---|---|
| 贪心（runtime `find_overall_index_fast`） | 65.0% | 85.5% |
| **匈牙利（`linear_sum_assignment`）** | **68.3%** | 83.2%（thr=0.3） |

贪心每轮取全局最大，不考虑"剩下的还能不能配上"，容易被单个高分干扰框带偏；
匈牙利求全局最小代价，天然保证一一对应。

> 注：匈牙利在 `thr=0` 时 point_hit 更高（86.6%）但 exact 只有 66.7%；
> `thr=0.3` 时 exact 最优。这说明"多配几个"和"配对正确"是两个目标，
> 线上应按 exact 选工作点。

### 5.6 定位过程中发现的五个坑（都很难靠"看代码"发现）

#### 坑 3：`main.jpg` 与标注图的版式不一致 —— 最隐蔽

采集器最初把 170×50 提示图 **resize 到 672 宽**（3.95 倍）拼到底部，
而 `autolabel_2408.py` 用**等比放置**（原尺寸贴左侧）。结果：

```
同一题，data/samples/<sid>/main.jpg          → 检测器 cls2 只出 1~2 个
同一题，data/labeled2408/images/<sid>.jpg    → 检测器 cls2 出满 3 个（召回 100%）
```

两张图肉眼"差不多"，但提示条里图标的位置/尺寸完全不同。
端到端验收一直在用 `main.jpg`，于是**验收结果与训练指标完全对不上**
（训练 val 召回 100%，端到端却只点对 65%）。

修法：`collect_2408.compose_main()` 改成与 `autolabel_2408.compose()` 完全一致的
等比放置。修复后同一题两张图的 class 分布完全一致（cls2=3, cls0=5）。

**教训：训练/验收/采集三处的版式合成函数必须共用同一份实现，不能各写一份。**

#### 坑 4：导出的 NMS 是跨类的，同类重复框仍会残留

`ultralytics export(nms=True)` 装进图里的是**跨类** NMS，
同一类内部的近重合框仍会输出（实测 60 题 335 个 class0 框里 10 对 IoU>0.5）。

重复框会占掉 `find_overall_index_fast` 贪心指派的列，直接破坏点击顺序
（这正是 `docs/TRAINING_AND_DATA_REFRESH.md` 5.4 记录的老问题，在本域同样存在）。

修法：`eval_2408.py --dedup 0.5` 在推理端对同类框再做一次 NMS。
实测重复框清零（10 对 → 0），`point_hit` 83.8%（+1.1 pt）。

#### 坑 5：小碎片进标签 = 纯噪声

分割器早期会把「两个方向都小」的残渣（21×24 / 23×25 / 28×20）当图标，
这类框检测器**学不出来**（实测 4 个 IoU=0.0 彻底漏检），
留在标签里只会拉低 precision。

修法：`min(w,h) < 18 and max(w,h) < 45` 的框直接丢弃。
注意**不能一刀切掉所有 min<30 的框** —— 细长字符（"1" 19×52、20×54）
是真实目标，它们长边 ≥ 45，必须保留。

#### 坑 6：匹配器学到了"尺寸差"而不是"形状"

`prepare_pairs_2408.py` 最初直接裁原图：a 侧（提示图标）**30×39**、
b 侧（底图框）**57×63**，差 1.9 倍。letterbox 到 112 后，
**尺度差异盖过了形状差异** —— 模型学到的是"大小不同"，不是"是否同一个图标"。

证据：val_acc 93.9%，但端到端单点命中只有 83.8%
（同尺寸的标注框上表现好，尺寸不一的检测框上就退化）。

修法：`--norm-short 64` 把两侧裁剪的最短边统一到 64px。
实测单点命中 83.8% → **87.2%**（+3.4 pt）。

#### 坑 7：随机初始化让匹配器立刻塌缩

```
[ep 1/12] loss=1.0215 val_acc=0.2500    ← 恰好 = 正样本比例 703/2794
[ep 2/12] loss=0.8566 val_acc=0.2500    ← 卡死
```

随机 backbone 的 576 维特征对「同一图标 vs 不同图标」几乎无区分度，
融合头只能学出常数解（全判负）。

修法：backbone 用 **ImageNet 预训练** `mobilenet_v3_small`（9.8 MB，首次自动下载）：

```
[ep 1/15] loss=0.7396 val_acc=0.7622 val_auc=0.9119 *
[ep 5/15] loss=0.1337 val_acc=0.9106 val_auc=0.9527 *
[ep 11/15] loss=0.0437 val_acc=0.9248 val_auc=0.9593 *
[ep 15/15] loss=0.0365 val_acc=0.9228 val_auc=0.9598
```

`--no-pretrained` 保留为开关，但默认必须开。

## 8. 已知待改进项（诚实记录）

1. **`exact_rate` 68.0%，主要损失在单点匹配（86.4%）**
   剩余错误分类：`wrong_pick` 16 / `order_shift` 9 / 框数偏多 6 / 漏检 1（60 题口径）。
   要把 exact 推到 90%+，单点必须到 0.97+。可尝试的方向：
   - 匹配器加难负样本比例（当前 1:2:1）
   - 用 `--from-pt weights/pre_model_v7.pt` 做 warm start（反解原结构）
   - 检测框 IoU 更严的导出侧 NMS

2. **`class 1 (title)` 没有训练数据**
   当前 runtime 不使用该类（2408 也没有标题元素）。若将来要识别「请依次点击」
   这类标题，需补标注。

3. **自动标注复核率 33.8% 偏高**
   是 `--review-thr 0.55` 的保守设定所致。实测真错配只有 3.9%。
   若要压低复核量，可把阈值调到 0.45 并抽查。

4. **匹配器仍是 mobilenet_v3_small + 新训融合头**
   没有用 `pre_model_v7.onnx` 反解权重做 warm start（那条路要处理 154 个
   `Identity` 别名节点，见 `docs/TRAINING_AND_DATA_REFRESH.md` 2.1）。
   实测预训练 + 15 epoch 到 val_acc 92.3% / AUC 0.960，够用。

5. **`--conf` 工作点只扫了粗网格**
   runtime 默认 0.3，本方案用 0.25（提示图标小、置信度偏低）。
   实测 0.15 反而更差（误检增多）。上线前应在固定评测集上细扫。

6. **采集命中率受 IP 风险等级影响**
   实测 22.2%。若被降级（2408 比例骤降），需要换出口或降频。
   `collect_report.json` 里的 `subcapclass_hist` 就是监控这个的。

7. **2401/2404 未处理**
   本方案只覆盖 2408（图标点选）。滑块 2401 与行为式 2404 需要完全不同的解法，
   不在本项目范围内。

8. **`main.jpg` 与标注图的版式依赖手工同步**
   虽然现在两处实现一致，但仍是**两份代码**（`collect_2408.compose_main`
   与 `autolabel_2408.compose`）。更稳的做法是抽到 `tools/layout_2408.py`
   共用。当前用「实测两张图的 class 分布必须一致」当回归断言（cls2=3, cls0=5）。

```powershell
cd T-Sec-captcha
$env:PYTHONIOENCODING='utf-8'
$env:POLARS_SKIP_CPU_CHECK='1'

pip install "polars[rtcompat]"

python tools/autolabel_2408.py --samples data/samples --out data/labeled2408 `
    --review-thr 0.55 --draw

# 4) 人工复核（看 data/labeled2408/review/*.jpg，改 review_queue.jsonl 对应的 pairs）
#    复核后重跑第 3 步

    --out data/pairs2408b --norm-short 64 --jitter 0.12

# 6) 重训检测器（40 ep ≈ 80 min）
python train/train_detector.py --data data/labeled2408/data.yaml `
    --epochs 40 --imgsz 640 --batch 8 --workers 0 --device cpu --cache ram `
    --project runs/detect --name t2408b `
    --out-onnx runs/export_t2408b/best_v3_2408b.onnx

# 7) 重训匹配器（15 ep ≈ 10 min）
python train/train_matcher.py --pairs data/pairs2408b --epochs 15 --batch 64 `
    --workers 0 --threads 8 --device cpu --auto-pos-weight `
    --project runs/matcher --name t2408b `
    --out-onnx runs/export_t2408b/pre_model_v7_2408b.onnx

    --limit 100 --conf 0.25 --dedup 0.5

# 9) 正式上线 + 冒烟
Copy-Item runs/export_t2408b/best_v3_2408b.onnx      model/best_v3.onnx -Force
```
