## 1. 应答码是什么（抓包实证）

点完确定后，前端向天御发校验请求：

```
POST https://turing.captcha.qcloud.com/cap_union_new_verify
```

返回 JSON：

```json
{"errorCode":"0","randstr":"...","ticket":"...","sess":"s0...", ...}   // 通过
{"errorCode":"12","randstr":"","ticket":"","errMessage":"","sess":"s0..."}  // 拒绝
```

判读要点：

| 字段 | 含义 |
|---|---|
| `errorCode` | **"0"=通过，非 0=拒绝**。本项目的关键判据 |
| `ticket` | 通过时有值，被拒时为空字符串 |
| `randstr` | 通过时有值，被拒时为空 |
| `sess` | 本次会话 id，可用于关联同一道题 |

注意 `ret` 字段在响应里**不存在**（源码里 `ret` 是内部构造的），
所以判读要用 `errorCode`，不要等 `ret`。

## 3. 可以提升准确率的方法（按证据强度排序）

### 方法 1：按应答码做「限流自适应」（收益最大，必做）

现在有了 `errorCode`，可以做成闭环：

```
连续 errorCode=12 达到 3 次  → 立即进入冷却（60s 起，指数退避）
冷却结束后先做 1 次探测        → errorCode=0 才恢复正式使用
```

实测依据：猛跑时 8/8 全 12，冷却 10 分钟后 4/4 全 0。
**这是把 30% 拉到 80%+ 的唯一有效手段**，且不需要改模型。

推荐参数：

| 参数 | 建议值 | 依据 |
|---|---|---|
| 单账号并发 | 1 | 多开会加速触发 |
| 两次登录间隔 | ≥ 45 s | 冷却 10 min 可完全恢复，45s 足够降速 |
| 触发阈值 | 连续 3 次 12 | 留 2 次余量避免误判 |
| 退避 | 60s → 180s → 600s | 实测 600s 可完全恢复 |
| 恢复探测 | 冷却后先试 1 次 | 避免整批浪费 |

### 方法 2：用 `ticket` 判定，而不是看弹层关没关

现在靠「弹层是否关闭 / URL 是否跳转」判断成功，会有延迟和误判。
改成监听 `cap_union_new_verify` 的 `errorCode`：

- `"0"` → 已验证通过，可以立刻提交业务登录
- `"12"` → 立刻放弃这道题并进入退避，**不要连续换题硬试**

这能把「每题判定」从秒级等待变成即时，也避免在风控期白白消耗题目。

### 方法 3：区分「答案错」与「风控拒」

目前只观察到 `0` 与 `12`。要区分答案错，需要继续收集：
在**未触发风控**时故意点错一次，看返回什么码（预期不是 12）。

拿到答案错的码之后，就能做分级处理：

| 码 | 处理 |
|---|---|
| 0 | 成功 |
| 答案错误码 | 重解同一道题（模型再算一次/换顺序） |
| 12 | 冷却，**不要重试** |

### 方法 4：单次登录内不要死磕同一题型

实测某次连续 3 道 2408 全 12，重开页面换到 2401 仍 12 ——
说明风控期换题型无效。应直接退避，而不是 `max-refresh` 反复试。
把 `--max-refresh` 从 3 降到 **1**，配合退避，总耗时和成功率都更好。

### 方法 5：2404 用站点真实字形（模型侧唯一明显短板）

| 题型 | 未触发风控时通过率 |
|---|---|
| 2401 滑块 | ~55%–63% |
| 2408 图标点选 | ~38%–45% |
| **2404 中文文字点选** | **~25%–33%** |

2404 现在是把标题文字用 `msyh.ttc` 渲染进提示条再匹配，字形与站点不一致。
若能从 sprite 裁出站点字形图替代渲染，应能明显提升。

### 方法 6：降低行为特征的机器性

`CloakBrowser` 已处理指纹，但点击节奏仍是程序化的。可加：

- 每题点击前的「阅读停顿」：800–2500ms 随机
- 点击间隔按「越靠后越慢」的分布，而不是均匀随机
- 偶发一次误点后自纠（真人会手抖）
- 整个登录流程的耗时分布向真人靠拢（当前稳定 30–40s，太整齐）
